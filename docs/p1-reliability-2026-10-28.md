# P1 发布权限、图片与故障恢复修复

## 改动

- `0005_private_content_trash.sql` 为内容增加 `is_deleted`，回填已有回收站状态。原表正文仅所有者可读；公开视图对撤回文档只提供不含标题、正文和素材的占位标记，阻止同 slug 仓库版本重新出现。公开标记会透露曾存在的 slug，不属于私密正文。
- Studio 回收站改用经过所有者认证的读取通道。保存、撤回和恢复同步写入数据库访问字段。
- 快速发布使用 Sharp 旋正并重新编码照片，生成最大边 480 / 1600 / 2560 的 WebP，默认剥离 EXIF/GPS 等来源元数据。原图继续保存在私有 bucket。新路径不覆盖当前发布的文件，上传失败不会切换展示指针。
- 公开图片改为 `/photographs/<uuid>`，每次请求重新查询已发布视图，只读取 derivatives。响应不缓存、不重定向到签名 URL。撤回后下一次请求返回 404；已被访客下载的内容无法收回。
- 图片入口也会重新编码旧版展示图，因此旧的原图复制件不会通过这个入口泄漏元数据。旧文件以及先前发出的签名 URL 不会自动消失；旧链接在原有有效期内仍可访问，已发出的旧 HTML 需部署后刷新。
- 云内容请求限制等待时间，失败保留服务端日志并交给公共错误边界，提供重试和可用导航。故障时不展示可能已撤回的仓库旧内容；这不是离线全文缓存。

## 应用顺序

1. 在已应用 0001–0004 的同一 Supabase 项目执行 `supabase/migrations/0005_private_content_trash.sql`。执行身份应为数据库管理者，公开投影视图刻意使用视图所有者权限，返回字段由 SQL CASE 限制。迁移撤销匿名原表读取；旧部署在切换完成前可能暂时无法读取云内容，建议安排维护窗口并紧接着部署。
2. 部署包含本次变更的应用，保留现有服务器环境配置。Sharp 已成为显式生产依赖。无需新建 bucket 或开放原图权限。
3. 未登录窗口验证撤回/恢复、图片和长时间停留；所有者验证旧回收站原文恢复、新照片上传发布。生产数据库和已发布页面验证与本地测试分别记录。

不要用公开视图恢复回收站正文；不要在云服务故障时自动回退到仓库内容；不要把 service-role key 放入浏览器。

## 本地检查

`npm run typecheck`、`npm run lint`、`npm run test:unit`、`npm run build`。

数据库权限验证脚本只连接一次性嵌入式 PostgreSQL：先在临时目录安装 `@electric-sql/pglite`，再运行 `node scripts/check-content-privacy.mjs <pglite 包的绝对路径>`。脚本应用原始 0004 和新 0005，验证匿名/非所有者隔离、既有数据回填、公开墓碑以及所有者恢复，不连接生产项目。

## 边界与后续

- 没有自动执行生产 SQL、部署或改变已有照片。需要部署后完成真实所有者流程。
- 稳定图片入口每次查询数据库与存储并编码，优先保证撤回和隐私正确；照片规模增长后可增加受控版本缓存，不能直接长期缓存可撤回的图片。
- 旧缩略图、旧签名链接和原图副本未做批量删除；历史存储清理属于后续独立工作。
- 云内容故障期间会显示重试页，不保证原文离线可读。没有依赖进程内“最后成功内容”，避免多实例不一致和撤回内容复活。
